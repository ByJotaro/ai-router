# Политика безопасности

## Поддерживаемые версии

Проект развивается в одном потоке: исправления выходят в `main`. Используйте
последнюю сборку.

## Как сообщить об уязвимости

- **Приватно**: GitHub → *Security* → *Report a vulnerability* (Private vulnerability reporting).
- Не открывайте публичный issue с деталями эксплуатации.

Опишите: версию/коммит, шаги воспроизведения, влияние, ожидаемое поведение.
Ответ — в течение 7 дней.

## Модель угроз и что считается уязвимостью

Шлюз по умолчанию слушает `127.0.0.1` и предназначен для локального/домашнего
использования. В области действия:

- обход аутентификации (`admin_token`, виртуальные ключи, allowlist моделей);
- утечка ключей провайдеров в логи, `state.db` в открытом виде, ответы API,
  сообщения об ошибках;
- SSRF/инъекции через `base_url` провайдера, заголовки, `tools`;
- обход квот виртуальных ключей;
- небезопасная десериализация конфига/состояния;
- path traversal в панели (экспорт журналов, файлы).

Вне области действия (by design):

- шлюз, выставленный в интернет без TLS-прокси и собственной аутентификации;
- компрометация самого хоста или WebView2;
- нарушение условий использования провайдеров (см. README, «Правовая оговорка»);
- DoS на локальном демоне без аутентификации при прямом доступе к порту.

## Как устроено хранение секретов

- `admin_token` генерируется при первом запуске и лежит в `config.yaml`.
- Ключи провайдеров хранятся в `config.yaml`; в `state.db` — в формате
  `enc:v1` (AES-GCM), если задан `STORAGE_ENCRYPTION_KEY` (`encryption.key_env`).
- Логи и CLI маскируют ключи; `internal/crypto/sanitize.go` вычищает их из
  сообщений об ошибках.
- Наружу уходит только запрос к выбранному провайдеру; телеметрии нет.
